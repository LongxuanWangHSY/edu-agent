# 智能教学 Agent — 架构设计文档 v1

> **文档性质：讨论稿，不是定稿。**
> 文中标 ❓ 的地方是**需要团队拍板**的决策项，标 💡 的是**我的建议**。请重点讨论第 2 节（架构主张）和第 6 节（待定决策）——那两节决定了后面所有实现。

## 0. 这份文档要解决什么

我们要做一个面向教师与学生的智能教学 agent。这个想法本身不复杂，复杂的是**怎么切分它**。

一个教学产品做久了必然会长出几十个功能：备课、出题、组卷、批改、错题本、讲评、学情分析、视频讲解、社区分享……如果一开始不把架构边界划对，三个月后它会变成一个谁都不敢改的单体应用，加一个功能要动五个地方。

这份文档给出的是**切分方案**：把什么做成可替换的插件、什么做成地基、什么做成上层编排，以及为什么这么切。

---

## 1. 项目是什么

### 1.1 一句话

一个**教学领域的 agent 运行时**：底层的教学能力（生成、判分、诊断、掌握度建模、渲染）做成可组合的插件，上层的教师 pack 与学生 pack 按需组装，两端共享同一套原语。

### 1.2 服务对象与场景

| 用户 | 核心痛点 | 期望能力 |
|---|---|---|
| **教师** | 备课耗时、出题难、批改慢、讲评缺乏针对性 | 教案生成、出题、组卷、批改辅助、学情报告 |
| **学生** | "我错在哪"说不清、复习没有重点、没人随时答疑 | 错题本、错因诊断、针对性变式、随时讲题、知识点总结 |

**两端共享的不是界面，是能力。** 教师出题和学生做题用的是同一个题目模型、同一个判分器、同一个知识图谱——这一点是架构设计的第一约束（见 §2.2）。

### 1.3 可复用的现有资产

本项目不是从零开始。已有资产（欧几里德之门内容项目）可直接迁移：

| 资产 | 内容 | 在新项目中的角色 |
|---|---|---|
| 写作技能体系 | 两阶段门控、六大文章模板、教学法规范 | **教案模块**的雏形与规范来源 |
| 教师视角审阅器 | 模拟一线教师审阅内容的 persona 与检查清单 | 可直接作为 agent 的 **teacher-persona** |
| 学生视角审阅器 | 模拟重点中学学生的阅读体验反馈 | 可直接作为 **student-persona** |
| 数学配图引擎 | TikZ/pgfplots/draw.io 路由 + 编译管线 + 出图质检 | **render 原语**的数学部分 |
| 题目验证实践 | 每道题用 Python 程序验证（数值代入、反例搜索） | **可验证性机制**（见 §2.5）的现成范式 |
| Manim 环境 | 程序化数学动画工具链 | **动画渲染**的实现路径之一 |

### 1.4 明确的非目标（首期）

写下来是为了防止范围蔓延：

- ❌ 不做非数学学科（但架构预留，见 §5.1）
- ❌ 不做直播、互动课堂、作业收发等"教学管理"功能
- ❌ 不做题库爬虫与版权内容聚合
- ❌ 首期不做社区（但数据格式必须为它做好准备，见 §2.6）

## 2. 架构主张

**这一节是文档的主干。** 以下六条是本架构的核心判断，也是最值得挑战的地方。

### 2.1 切原语，不切功能

**参照对象要看清粒度。** DeepSeek Harness（`~/.dsh/`）约 200 个插件包，每个只做一件事：`dsh-fs-local`（本地文件读写）、`dsh-tool-bash`（执行 shell）、`dsh-session-persistence-jsonl`（会话存储）、`dsh-sandbox-windows-acl`（平台沙箱）。它连 LLM provider、存储后端、沙箱实现都是可替换插件。

而"出题""组卷""错题本"是**用户看得见的功能**，不是原语。按功能做插件，会得到 **7 个假装成插件的单体**——插件架构的复杂度全背上（生命周期、依赖注入、版本兼容），模块化的好处一点没拿到：因为"出题""改题""组卷"三个插件会各自实现一遍题目表示、知识点标注、难度标定、答案生成。

**正确的切法是找共用的原子能力。** 判据：**如果一个能力被 ≥2 个功能用到，它就是原语；如果一个"功能"能由若干原语编排而成，它就属于工作流层，不是插件层。**

### 2.2 错题本是地基，不是插件

除错题本外，其余功能都是**无状态生成任务**：给输入、出内容、结束。

错题本是**有状态数据系统**：跨会话、跨设备、时间序列、复习调度、统计报表。它要求数据模型、迁移策略、同步冲突解决、备份恢复。

无状态插件好做，有状态系统难做。**把错题本当第 N 个插件，等于把整个项目最难的部分伪装成最简单的那部分。**

### 2.3 形态无关：只有一个层知道"用户在哪"

产品形态尚未决定（Web / 本地 harness / 桌面 / 小程序，❓见 §6.1）。这不是混乱，是**保留了选择权**——但前提是架构必须形态无关。

做法：**形态适配器放最外层**，内核完全不知道自己在哪运行。

```
L0  CLI 适配器 | Web 适配器 | 桌面适配器 | 小程序适配器   ← 唯一知道形态的一层
─────────────────────────────────────────────────────
L1+ 能力层：完全形态无关
```

**反面教材**：把"生成教案"直接写进某个 Web 路由处理器里。这样一旦要出桌面版，教案功能就得重写。

### 2.4 双端差异只能出现在工作流层

既然两端共享能力，就要有一条**可检验的红线**：

> 如果发现"学生端需要单独实现一套判分"或"教师端需要单独实现一套出题"，
> 说明原语层切错了，应当回去修原语，而不是在两端各写一份。

这条红线是架构健康度的第一个体检指标。

### 2.5 可验证性是数学内容的生命线

AI 生成数学内容**出错很难被发现**——文字错误读者能看出来，数学错误往往只有算过才知道。已有前车之鉴：某篇文章曾写入一个错误的几何命题（"最远点对覆盖圆"），直到读者发现才被纠正。

**因此：AI 生成的题目必须过一遍自动验证才允许入库。**

验证手段（按可行性排序）：

1. **数值代入**：把答案代回题设，检验等式/不等式是否成立
2. **反例搜索**：对命题类内容，随机/穷举搜索反例（已有实践）
3. **符号计算**：用 sympy 独立求解，与生成答案比对
4. **约束校验**：题目自身的自洽性（选项唯一、参数范围合法、图形可构造）

**这是本产品与"普通 AI 出题工具"最本质的区别。** 没有这一层，产品只是"生成得很快"，而不是"生成得可靠"。

### 2.6 社区的成立前提在第一阶段的 schema

LeetCode 的社区能成立，**不是因为它有论坛**，而是因为它的题目是**机器可评测的**——有标准输入输出、有判题机、因此可以排序、可以复用、可以"通过率倒数第一"这样的社区梗。

教学设计、出的题如果没有这个标准，UGC 会退化成"一堆无法复用、无法验证、无法排序的文本"。

所以：**社区功能可以晚做，但支撑社区的数据格式必须现在定。** 好消息是这件事和插件架构不冲突——`item` schema 的 manifest 化设计（见 §5.1）同时服务于插件组装和社区分享。

## 3. 分层架构

### 3.1 五层

```
┌─────────────────────────────────────────────────────────┐
│ L4 应用包   teacher-pack / student-pack                  │  ← preset 组装
├─────────────────────────────────────────────────────────┤
│ L3 工作流   备课流 · 出题流 · 组卷流 · 诊断复测流 · 讲评流   │  ← 编排；两端在此分岔
├─────────────────────────────────────────────────────────┤
│ L2 原语     item · kg · gen · grade · mastery · render   │  ← 真插件层
├─────────────────────────────────────────────────────────┤
│ L1 地基     数据模型 · 存储 · 合规 · 模型接入 · 权限         │  ← 不做完不启动上层
├─────────────────────────────────────────────────────────┤
│ L0 形态适配 CLI · Web · Desktop · MiniProgram             │  ← 唯一知道形态的一层
└─────────────────────────────────────────────────────────┘
```

### 3.2 层间契约

| 层 | 只能调用 | 禁止 |
|---|---|---|
| L4 应用包 | L3 工作流、L2 原语 | 直接写数据库、直接调 LLM |
| L3 工作流 | L2 原语 | 绕过原语自己实现生成/判分逻辑 |
| L2 原语 | L1 地基、其他原语（通过声明依赖） | 感知形态（UI、HTTP、会话） |
| L1 地基 | 无（最底层） | 包含业务规则 |
| L0 形态适配 | L3/L4 的对外接口 | 任何业务逻辑 |

### 3.3 怎么知道分层切对了

三条自检：

1. **新增一个学科**，是否需要改 L2 以上任何一层？不应该需要（学科是数据，不是代码）。
2. **新增一个功能**（比如"听写练习"），是否可以只写 L3 编排、不动 L2？应该可以。
3. **两端能否共用同一个原语实例**？如果教师端和学生端各自初始化了一套 `item` 服务，说明切错了。

## 4. 原语层设计

### 4.1 原语清单

| 原语 | 职责（**只做这些**） | 明确不做 |
|---|---|---|
| `item` | 题目与教学资源的统一表示 + 校验 | 不生成、不判分、不存储 |
| `kg` | 知识图谱：节点、先修关系、关联强度 | 不管掌握度 |
| `gen` | 生成：题、变式、讲稿、教案骨架 | 不判分、不落库 |
| `grade` | 判分 + **错因诊断**（概念/计算/审题/方法） | 不管复习调度 |
| `mastery` | 学生掌握度模型 + 间隔重复调度 | 不生成内容 |
| `render` | 渲染：数学图 / 排版 / 动画 / 幻灯片 | 不决定内容 |
| `store` | 持久化（后端可替换）+ schema 迁移 | 不含业务逻辑 |
| `policy` | 合规：同意管理、数据分级、导出与删除 | 不碰业务 |

下面只展开**接口最关键的三个**，其余同理。

### 4.2 关键契约：`gen` 的输入输出都是 `item`

这是整个原语层最重要的一条约定：

```
gen.derive(item, 变换类型) -> [item...]      // 变式
gen.compose(要求, 约束)     -> [item...]      // 出题
gen.explain(item, 学情)     -> 讲稿           // 讲题/讲评
gen.lesson(知识点, 课时)     -> 教案骨架
```

**为什么这条重要**：出题、改题、组卷、错题本变式，本质都是"从 item 生成 item"。统一成同一种输入输出后，这四个工作流共享同一个生成原语、同一套验证管线、同一种存储——而不是各写一套。

### 4.3 `grade`：判分器还是诊断器？

❓ **待决**（见 §6.4）。我的建议 💡：**做成诊断器，判分是它的特例。**

```
grade.check(item, 学生作答) -> 判定              // 对/错/部分对
grade.diagnose(item, 学生作答) -> 诊断 {
    判定,
    错因分类: 概念不清 | 计算失误 | 审题偏差 | 方法选择错误 | 表达不规范,
    错在哪一步: [steps],
    涉及知识点: [kpoint_id],
    置信度
}
```

理由：学生最痛的是"我错在哪"，教师最痛的是"怎么讲评"，两者要的都是**诊断**而非分数。把判分当主接口，后面一定要重构。

### 4.4 `mastery`：掌握度与调度

```
mastery.update(学生, kpoint, 诊断结果) -> 掌握度
mastery.due(学生, 时间)                -> [待复习 kpoint]
mastery.weak(学生, 阈值)                -> [薄弱 kpoint]
mastery.plan(学生, 目标)                -> 复习计划
```

**注意**：掌握度是**推论**不是**事实**，模型必然不完美。接口设计上要允许替换算法（先做简单版：正确率 + 遗忘曲线；以后可换更复杂的模型）。

### 4.5 `render`：外部渲染器适配层

产品要做教学视频，计划复用 GitHub 上的开源项目（❓具体是哪个待定，见 §6.3）。这意味着 `render` **不能把任何一种渲染实现写死**，它必须是一个适配层：

```
render.register(渲染器实现)                     // 插件式注册
render.figure(数学结构, 风格)  -> 图片
render.animate(推导过程, 时长) -> 视频
render.typeset(item集合, 版式) -> 试卷/讲义
```

已确定要有的实现：**数学图（TikZ/pgfplots）**、**动画（Manim）**。待接入的：开源视频生成项目。**接入新渲染器不应该改动任何其他原语。**

## 5. 数据模型

### 5.1 `item` schema — 地基中的地基

**它必须同时满足三件事，缺一不可：**

1. **人能读** —— 能直接排进教案和试卷
2. **机能判** —— 有形式化答案 + 判分器接口
3. **网能传** —— 可版本化、可 fork、可组合（社区的前提）

```
Item {
  id, version, parent_id?          // 版本与变式溯源
  meta {
    学科, 学段, 题型, 预计用时, 语言
    // 学科是【数据】不是代码——新增学科不改任何一层（§3.3 检验 1）
  }
  stem: 富文本 + 数学表达式
  options?                          // 选择题
  answer: AnswerSpec
  analysis: 解析
  knowledge: [kpoint_id]            // 知识点标签，指向 kg
  difficulty: {标定值, 样本正确率, 样本量}
  verifiers: [VerifierSpec]         // ★ 机器可验证的断言，见下
  assets: [图/动画引用]
  provenance {来源, 作者, 许可, 生成方式, 验证状态}
}

AnswerSpec {
  形式: 精确值 | 区间 | 表达式 | 选项 | 证明要点
  value
  grader_id                         // 指向判分器实现
}

VerifierSpec {                      // ★ 可验证性是本产品的核心资产
  类型: 数值代入 | 反例搜索 | 符号计算 | 约束校验
  表达式 / 搜索空间 / 约束
  上次验证时间, 结果
}
```

**`verifiers` 字段是整个 schema 的灵魂**（对应 §2.5）。一道题带不带机器可验证的断言，决定了它能不能被信任、能不能被自动生成、能不能在社区里被排序。

**「可验证比例」应当是一个可观测的产品指标。**

### 5.2 知识图谱

```
KPoint { id, 学科, 名称, 别名[], 描述 }
Edge   { from, to, 类型: 先修 | 包含 | 关联, 强度 }
```

**成本警告**：知识图谱是全项目**最贵**的资产——它不能靠 AI 一次性生成（会幻觉出不存在的关系），需要人工校准。数学先行是正确的（高中知识点约几百个，可控）；预留多科时，**图谱要能按学科独立加载**，不要一开始就做全球统一图谱。

### 5.3 掌握度模型

```
Mastery { 学生id, kpoint_id, 估计值, 置信度, 最后一次接触, 历史[] }
```

建议首期用最简单的模型（正确率 + 遗忘曲线），**接口留好**即可。不要在掌握度建模上过早投入——它需要真实数据才能调优，而首期没有数据。

### 5.4 判分器接口

```
Grader {
  适用题型
  check(item, 作答) -> 判定
  诊断(item, 作答)  -> 诊断结果
}
```

**分级策略**：
- 客观题（选择/填空）：规则判分，准确可靠
- 计算题：符号计算比对（允许等价形式）
- 证明题/解答题：**只能诊断，不能判分**——输出"你这一步的逻辑是……，可能的问题在……"，而非"你得了 7 分"

诚实很重要：**做不到的事不要在界面上假装能做到。**

## 6. 待定决策

### 6.1 技术栈 ❓

三条路线，团队讨论定。

| | **路线 A：Python 为主** | **路线 B：TypeScript 为主** | **路线 C：混合** |
|---|---|---|---|
| **核心优势** | 数学生态原生（sympy / manim / networkx / numpy / matplotlib）；现有资产直接复用（MCP 服务器、验证脚本、manim_env） | 可直接借鉴 dsh 的 cordis 插件机制、依赖注入、生命周期；多形态交付（Web/桌面/小程序）语言统一 | 各取所长 |
| **核心劣势** | 插件生态弱（DI/插件机制要自造）；教师端分发（桌面/小程序）困难；前端要另配语言 | 数学生态弱，sympy/manim 必须跨进程调用 Python；符号计算与动画是硬需求，绕不开 | 通信、部署、调试复杂度翻倍；小团队维护成本高 |
| **适合的形态** | 本地 CLI / harness 型产品 | Web / 跨端产品 | 长周期、团队规模较大 |

💡 **我的建议：路线 C，但用一个已经验证过的简单边界——把 Python 引擎暴露成 MCP server，外壳用 TS 或任何语言。**

理由是三条：

1. **数学生态不可替代**。sympy 的符号计算、manim 的动画、已有的 TikZ 管线——这些没有等价的 JS 实现，无论如何都要有一个 Python 进程。
2. **MCP 就是现成的边界协议**，而且项目已经在用（现有 5 个 Python MCP 服务器）。引擎按 MCP 暴露，CLI、Web、桌面、小程序都能挂——**这恰好满足"形态保留每种可能"的要求**，而且不需要自己发明 RPC 协议。
3. **复杂度是可控的**：边界只在原语层之上，L3/L4 完全可以只活在一侧。

**但这条路线的前提是 §3.2 的层间契约被严格执行**——一旦业务逻辑漏进 Python 侧或外壳侧，混合架构的复杂度就会失控。

### 6.2 学生数据合规 ❓

面向未成年学生的错题本 + 学习行为数据，直接落在《个人信息保护法》与《未成年人网络保护条例》（2024-01-01 施行）上。

**这不是后期优化项，是第一天就要设计的约束。** 需要明确：

- 监护人同意机制
- 最小必要采集（哪些数据真的必须有？）
- **本地优先还是云端优先**——本地优先架构更重但后续不返工
- 删除权与导出权的实现
- 明确不用于模型训练

💡 建议：**姿态上"本地优先、云端可选"**。这不仅满足合规，也是产品差异点——**"你的学生的数据不会被拿去训练模型"是一句教师会相信的话**。

### 6.3 视频渲染接入哪个开源项目 ❓

已决定复用现有开源项目而非自研。需要团队评估后确定，评估维度：

- 能否从**结构化数据**渲染（而不是只接受自然语言提示）——这决定了它能不能接进 `gen → render` 管线
- 数学内容的保真度（公式渲染、图形准确性）
- 许可协议是否允许商用/二次分发
- 输出可控性（时长、分镜、配音）
- 运行成本（自托管 vs API 计费）

**架构上已为此留好位置**：`render` 是适配层（§4.5），接入新渲染器不改动其他原语。

### 6.4 `grade` 的主接口 ❓

判分器 vs 诊断器 —— 见 §4.3。💡 建议诊断器优先。

## 7. 落地路径

### 7.1 先打通一条闭环，不做七个功能的广度

```
出题 → 学生做 → 诊断错因 → 归类到知识点 → 生成针对性变式 → 复测
```

**为什么选这条闭环**：

- 它**同时压测了原语层的六个模块**（item / kg / gen / grade / mastery / render），任何切分错误会立刻暴露
- 它是教师和学生**共同的**痛点（教师最痛的是讲评，学生最痛的是"我错在哪"）
- 它自带验证：闭环跑不跑得通，一试便知，不需要等用户反馈
- **广度后补容易，闭环打通难**

### 7.2 里程碑

| 阶段 | 目标 | 完成判据 |
|---|---|---|
| **M0** | 数据模型定稿 | `item` schema + `Grader` 接口定稿，能表示 20 道真实题目 |
| **M1** | 闭环原型（命令行） | 一条命令走完闭环：出题→作答→诊断→变式→复测 |
| **M2** | 可验证性机制 | AI 生成的题目 100% 过验证才入库；能统计"可验证比例" |
| **M3** | 教师 pack | 备课流 + 出题流可用，能产出可直接用于课堂的材料 |
| **M4** | 学生 pack | 错题本 + 诊断 + 复测可用 |
| **M5** | 形态适配 | 第一个正式形态（Web 或桌面）上线 |
| **M6** | 社区 | 前提是 §5.1 的 schema 已稳定 |

**M0 和 M1 之间不要跳。** 数据模型没定就写功能，是这类项目最常见的死法。

## 8. 风险清单

| 风险 | 后果 | 缓解 |
|---|---|---|
| **知识图谱建得太慢** | 拖住所有上层功能 | 数学先行；图谱按学科独立加载；允许"未标注"状态存在 |
| **AI 生成内容不可信** | 产品口碑崩（教师发现题是错的） | §2.5 可验证性机制，过硬验证才入库 |
| **插件切错粒度** | 架构复杂度全背上，好处没拿到 | §2.1 判据；§3.3 三条自检 |
| **合规事故** | 产品级灾难 | §6.2，第一天设计 |
| **双端并行导致资源分散** | 两端都做不透 | 原语层强制共享（§2.4）；pack 层允许一端先做深 |
| **过早做社区** | 建了一个没人用的论坛 | 社区只在 schema 稳定 + 有真实内容存量后启动 |
| **视频模块成本失控** | 烧钱且质量不稳 | 优先程序化动画（可验证、可复现、边际成本近零）；外部项目评估后再接 |

## 附录：术语表

| 术语 | 含义 |
|---|---|
| **原语（primitive）** | 被 ≥2 个功能复用的原子能力，是插件的单位 |
| **工作流（workflow）** | 由原语编排而成的完整任务链，是两端的分岔点 |
| **应用包（pack）** | 面向一类用户的组装预设（教师 pack / 学生 pack） |
| **物品（item）** | 题目与教学资源的统一表示，本架构的核心数据结构 |
| **可验证性（verifiability）** | 内容能否被机器独立检验真伪，本产品的核心资产 |
| **形态适配器** | 最外层、唯一感知运行环境（CLI/Web/桌面/小程序）的组件 |
